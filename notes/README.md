# 笔记规范

## 三条核心规则

### 1. 一个文件说清一件事

**开头第一段就写结论**，不要写成推理过程再在末尾揭晓。以后回来查阅时，你只想知道答案。

### 2. 带时间戳

环境类、工具类的结论**会过时**。没有日期的「事实」会误导未来的你。

```markdown
> 实测时间：2026-10-11
```

本项目已经踩过这个坑：README 里一度写着「`git push` 网络层封死，与权限无关」，
后来网络恢复，同一批测试从 0/5 变成 5/5。**那次错误结论就是因为当成永久事实写了。**

### 3. 写明依据

区分**实测**和**推测**：

| 写法 | 含义 |
|---|---|
| `实测：curl 返回 403` | 有原始证据，可信 |
| `推测：可能是因为…` | 未验证，需要复核 |
| `据 X 文档` | 二手来源，附链接 |

不要把推测写成实测。**这是这个笔记库最重要的纪律**——排查过程中最容易犯的错，
就是把「当前观察到的一次结果」升级成「系统的固有性质」。

## 命名

- 用能直接读懂的短句：`github-access.md`、`windows-凭据管理.md`
- 不要 `untitled`、`新建文档 2`、`test`
- 同一主题多个文件时用目录分组

## 分类

| 目录 | 放什么 |
|---|---|
| `notes/` 根 | 跨主题的、还没归类的 |
| `notes/env/` | 环境、配置、网络、凭据、排查过程 |
| `issues/` | 需要长期跟进的事项（不是 bug 报告） |

新增分类前先想想：**能不能并进已有的？** 目录太多比太少更难找。

## 维护

- 结论被推翻时，**不要删掉旧结论**——改成「~~旧结论~~ → 更正为…」，保留纠错痕迹
- 因为**知道自己是错的，比一直以为自己对更有价值**
